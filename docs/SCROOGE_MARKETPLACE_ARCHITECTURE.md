# «Скрудж Макдак» — архитектура и план реализации

## Цель

Единая барахолка в Telegram и ВКонтакте: пользователи создают объявления через ботов, администрация проверяет их из единого центра, а публикации и рассылки отправляются в выбранные каналы и аудитории.

## Текущая отправная точка

Репозиторий уже содержит VK Callback API, SQLite, создание и редактирование объявлений, модерацию, поиск, жалобы, архив, ограничения частоты и роли. Telegram-бот в исходном состоянии репозитория не обнаружен. Изменения должны сохранять существующую таблицу `users` и данные SQLite.

## Архитектура

- **Telegram adapter:** aiogram 3; анкета товара, фото, мои объявления, уведомления, административные действия.
- **VK adapter:** существующий FastAPI Callback API и VK API client.
- **Shared moderation service:** единая очередь, внутренний ID объявления, атомарные переходы статусов, журнал действий и причина отклонения.
- **Persistence:** SQLite на текущем этапе. Существующая схема VK сохраняется; Telegram-специфичные идентификаторы и объявления добавляются отдельными таблицами, чтобы избежать небезопасного перестроения таблицы `users`.
- **Publication:** Telegram-объявления публикуются в настроенный Telegram-канал; VK-объявления — на стену сообщества. Не публиковать повторно при уже изменённом статусе.
- **Announcements and broadcasts:** администратор выбирает тип сообщения, платформу и аудиторию; сохраняются кампания, результаты и ошибки доставки.
- **Runtime:** один Pterodactyl процесс запускает FastAPI/VK Callback API и, если задан `TELEGRAM_BOT_TOKEN`, Telegram polling.
- **Configuration:** секреты только через environment variables; реальные токены не добавлять в Git.

## Статусы объявлений

`draft → moderation → publishing → published`

Дополнительные конечные состояния: `rejected`, `archived`, `deleted`. Переходы должны проверять исходный статус в SQL, чтобы два администратора не опубликовали одно объявление одновременно.

## Этапы реализации

1. **Аудит и защита текущего поведения:** не менять существующую VK-схему разрушительным способом; проверить конфигурацию и точку запуска.
2. **Модели Telegram:** таблицы пользователей, объявлений, подписок и рассылок; безопасная и повторно запускаемая инициализация.
3. **Telegram-подача объявления:** название, категория, описание, цена, город, до 5 фото, предпросмотр, отмена и отправка на модерацию.
4. **Единая очередь:** в административном интерфейсе Telegram отображаются ожидающие VK- и Telegram-объявления; действия проверяют роль администратора.
5. **Публикация:** публикация в платформу-источник; Telegram-канал задаётся через `TELEGRAM_CHANNEL_ID`. Не считать объявление опубликованным, если внешний API завершился ошибкой.
6. **Новости и рассылки:** администратор выбирает тип, платформу и аудиторию; подписчики могут отписаться; недоставленные сообщения логируются и не приводят к остановке всей кампании.
7. **Тестирование:** проверки валидации, миграций, доступа, повторной модерации, ошибок API и рассылок; CI на Python 3.12.
8. **Развёртывание:** обновить `.env.example`, проверить startup в Pterodactyl, health endpoint, логи и восстановление после перезапуска.

## Обязательные критерии готовности

- Старые VK-данные остаются доступными после запуска новой версии.
- Отсутствие Telegram-токена не ломает существующий VK-сервис.
- Неавторизованный пользователь не может выполнять административные callback-действия.
- Ошибка Telegram/VK API не оставляет объявление ложно помеченным как опубликованное.
- В рассылке обрабатываются блокировки, запрет личных сообщений и лимиты API; не выполняется обход пользовательского отказа.
- В CI запускаются синтаксическая проверка и тесты. Успех локальных/CI-проверок не заявляется без фактического результата.
